# 0006 — 岗位库双源分发:岗位包为默认源,维护者文档永不分发

- 状态:已接受(2026-09-11);2026-09-12 追记「用户自助文档源」(见文末)

## 背景

控制台岗位库的岗位内容由上游供给。初版直接绑定维护者自己的腾讯智能表格(匿名读取,文档需「有链接即可查看」)。若开源给所有用户,只有两条路:每个用户绑定自己的文档(大部分用户没有、也不想维护),或者暴露维护者的文档地址(文档一旦改权限/删除,全部用户的数据通道同时断掉;且地址是维护者的私人资产)。

可选:用户各自绑定自己的文档 / 全员共享维护者文档直连 / 维护者导出数据快照分发。

## 决策

**双源制**:岗位源(Source)分两种——

- **岗位包(pack,默认)**:维护者导出的数据快照(jobs-pack.json)随仓库与安装包分发。用户零配置,点「同步」即从公开仓库 raw 直链拉最新,失败回落随包内置版本;`jobs.json` 的 `packUrl` 可换远程地址。
- **我的文档(doc,仅维护者)**:绑定腾讯智能表格直读,登录态/文档地址只存维护者本机。

对外分发铁律:**文档地址永不出维护者机器**。岗位包默认剥离内推码/联系人字段并清洗链接里的内推参数(`--full` 保留),岗位 ID 按清洗后内容重算。发布走流水线(同步→防呆→打包→推送),岗位数异常自动拦截。

## 后果

- 用户的岗位数据新鲜度取决于维护者的发布节奏,产品语义上这是「策展内容」,README 需如实标注「尽力而为」;
- 维护者停止维护即全部用户数据停更——内容单点依赖是该模式的固有代价,靠发布流水线把维护成本压到最低;
- 内推码对公开用户不可见是刻意的:内推是他人给的资源,默认不随开源扩散;维护者可用 `--full` 导出完整版供私密渠道;
- 用户侧永远不需要腾讯文档账号,隐私叙事(数据不出本机)不被破坏——拉取的是公开文件,不上报任何用户数据。

## 追记(2026-09-12):用户自助文档源

真实用户提出需要接入**自己手里**的腾讯智能表格(学校群/朋友分享的内推表),而非只消费原厂岗位包——覆盖面缺口是结构性的(策展视角无法覆盖所有专业方向)。

**追记决策**:开放「用户自助文档源」——岗位源从单数变列表,用户可在控制台添加任意「有链接即可查看」的腾讯智能表格(试读预览确认表头可识别后入库,手动分源同步,可移除)。原厂岗位包仍为默认源且不可移除;**发布岗位包只消费维护者主文档源**,用户自助源的内容永不进入岗位包。

边界(不因开放而改变):仅限公开可读的表、仅限手动同步、绝不自动轮询;表头认不出「公司/岗位」即拒绝(宁缺毋滥);用户自助源与原厂包按来源分桶,互不覆盖。

**后果**:表结构多样性由「列映射三级兜底 + 试读预览人工确认」消化,失败的表明确报错不静默;「仅自己可见」的表仍不可读——该场景留给未来的浏览器插件路线,当前不做。

## 追记二(2026-09-12):识别投递网址 + 私密文档登录通道

「一键收录」插件的核心能力以移植方式进入控制台,而非插件桥接:**识别投递网址**(JSON-LD/og/选择器三级提取 + 城市/岗位推断)由控制台原生无头浏览器执行,结果经预览人工确认后落内建「手动收录」源——只存本机、永不进岗位包;插件保持台账专属不动。私密文档源改由「登录腾讯文档」(docsqq 持久 profile 扫码一次)打通,同样不引入插件。

## 追记三(2026-09-12):识别入口收敛为插件

控制台内的「🔍 识别网址」粘贴式入口与 `POST /api/jobs/capture` 路由移除——识别入口统一为「岗位收录助手」插件(页内识别 → 跳 `/console?capture=` 承接确认,或直接收录)。确认弹窗与 `/api/jobs/capture/save` 保留为承接落点;`ats jobs capture <url>` CLI 与 jobcapture.mjs 识别引擎保留(dev 工具,无 UI 面)。
